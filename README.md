# Dynamic Regulation Policy Compiler

把版本化法规和机构规则编译为确定性的后端决策策略，面向需要可追溯决策的服务端系统。

## 环境与启动

需要 Python 3.12+。

```bash
python -m pip install -e ".[dev]"
uvicorn regulation_policy_compiler.app:app --host 0.0.0.0 --port 8000
pytest
```

## 公开接口

- `GET /health`：返回 `{"status":"ok"}`，用于进程健康检查。
- `regulation_policy_compiler.policy.evaluate(at, facts, rules)`：对版本化规则做确定性求值，返回 `(decision, trace)`。
- `regulation_policy_compiler.policy.compile_rules(at, rules)`：复用 `evaluate` 的校验、`[from,to)` 生效选取、每 `(source,id)` 取最高 `ver` 与排序，返回深副本 `{"at","rules","conflicts"}`；`conflicts` 按排序下标 `i<j` 列出结果不同且 `when` 条件可同时成立的规则对（前项为 winner）。
- `POST /rules/compile`：请求体为恰含 `at,rules` 的 JSON 对象；非法请求响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行）。
- `regulation_policy_compiler.policy.policy_attestation(at, rules)`：`at`、`rules` 校验同 `compile_rules`，任一类型、时间、规则字段、`[from,to)` 区间或重复 `(source,id,ver)` 错误均抛 `ValueError` 且不改输入。先取 `compile_rules(at,rules)` 结果 `policy`，返回深副本，顶层键序 `at,policy,digest`，`policy` 逐层保持 `compile_rules` 的全部键序、排序、`when` 键 Unicode 码点升序及 `conflicts` 顺序。令 C 为 `json.dumps(policy,ensure_ascii=False,separators=(',',':'))` 的 UTF-8 字节（无换行），`digest` 为 C 的 SHA-256 小写十六进制 64 字符；相同值输入须得逐字节相同结果。
- `POST /rules/attest`：请求体为恰含 `at,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史。
- `regulation_policy_compiler.policy.policy_delta(from_at, to_at, rules)`：`from_at`、`to_at` 须为合法 UTC 秒且 `from_at<=to_at`，`rules` 校验同 `compile_rules`，任一非法抛 `ValueError` 且不改输入。分别编译两时点并以 `(source,id)` 标识入选规则，返回深副本，顶层键序 `from,to,rules,conflicts`。`rules` 仅含 `added`（仅后有）、`removed`（仅前有）、`updated`（均有但完整值不同），相同者省略，按 `source` 的 `law`、`org` 顺序及 `id` Unicode 码点升序；项键序 `source,id,kind,before,after`，`before`/`after` 为对应编译规则快照或 `null`。`conflicts` 键序 `added,removed`，以 `winner` 数组后接 `loser` 数组的六元值为身份，`added` 按后时点编译冲突原序列出仅后有项，`removed` 按前时点原序列出仅前有项；冲突项键序 `winner,loser`。无差异时 `rules=[]` 且 `conflicts` 两数组均空。
- `regulation_policy_compiler.policy.policy_schedule(start, end, rules)`：`start`、`end` 须为合法 UTC 秒且 `start<=end`，`rules` 校验同 `compile_rules`，任一非法抛 `ValueError` 且不改输入。候选时点为 `start` 及规则中落在 `(start,end]` 的 `from` 与非空 `to`，去重升序后逐点调用 `compile_rules`；首点必保留，后续计算 `policy_delta(上一保留点时间, 当前候选时间, rules)`，仅当其 `rules=[]` 且 `conflicts` 的 `added`、`removed` 均为空时丢弃，否则保留。返回深副本，顶层键序 `start,end,points`；点键序 `at,rules,conflicts,delta`，`rules`、`conflicts` 取该时点 `compile_rules` 同名值并保持逐层契约；首点 `delta=null`，后续点 `delta` 为上述 `policy_delta` 的完整结果。
- `POST /rules/schedule`：请求体为恰含 `start,end,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史。
- `regulation_policy_compiler.policy.policy_schedule_attestation(start, end, rules)`：`start`、`end`、`rules` 的校验及异常同 `policy_schedule`（抛 `ValueError` 且不改输入）。令 S 为其 `policy_schedule` 结果，返回深副本，顶层键序 `start,end,root,points`；`start`、`end` 取 S，`points` 与 S.points 同序，项键序 `at,rules,conflicts,delta,previous,digest`，前四项逐层等于 S 对应点并保持键序。首项 `previous` 为 64 个 ASCII 字符 `0`，后项取前项 `digest`；令 C 为当前项仅含 `at,rules,conflicts,delta` 且按此键序执行 `json.dumps(...,ensure_ascii=False,separators=(',',':'))` 所得无换行 UTF-8 字节，`digest` 为 `previous` 的 ASCII 字节紧接 C 所得 SHA-256 小写十六进制，`root` 取末项 `digest`；等值输入须逐字节相同。
- `POST /rules/schedule/attest`：请求体为恰含 `start,end,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史。
- `regulation_policy_compiler.policy.verify_policy_schedule_attestation(report, expected)`：纯函数校验调度哈希链报告，不访问文件、不改输入。`report` 恰含 `start,end,root,points`；`start`/`end` 为合法 UTC 秒且 `start<=end`，`root` 为 64 位小写十六进制字符串，`points` 为非空数组，逐层符合 `policy_schedule_attestation` 返回契约的精确键集、类型和值域（规则快照、`winner`/`loser` 冲突三元组及后续点完整 `policy_delta` 结构均按契约校验）；点 `at` 严格递增、落在闭区间 `[start,end]`，首点 `at=start` 且 `delta=null`，各点 `previous`/`digest` 为 64 位小写十六进制字符串。除结构校验外还做语义校验：点内 `rules` 各项在该点 `at` 落入 `[from,to)`（`to` 为空则不限）、`(source,id)` 唯一、按 source（law 先于 org）、priority 降序、from 降序、id 的 Unicode 码点升序、ver 降序精确排列；`conflicts` 须等于由该点 rules 按下标 i<j（result 不同且 when 可同时成立，前者为 winner）重建的冲突序列，缺失、伪造、重复、乱序均非法。后续点 `delta` 的 `from`/`to` 须分别等于前点/本点 `at`；`delta.rules` 须按 source（law 先于 org）、id 码点升序精确列出相邻快照的 added（前空后非空）、removed（前非空后空）、updated（两端非空且值不同），项键序 `source,id,kind,before,after` 且无重复、无遗漏；`conflicts.added` 按本点冲突原序、`conflicts.removed` 按前点冲突原序，精确等于 winner 数组接 loser 数组的六元身份差集；后续点 delta 不得三者皆空。`expected` 恰含 `start,end,root` 并同法校验；上述任一非法（含语义违规）均抛 `ValueError`。先按既有契约重建所有字典键序（规则 `when` 键按 Unicode 码点升序），再按 `policy_schedule_attestation` 定义逐点重算：首项 `previous` 为 64 个 ASCII 字符 `0`，后项取前项 `digest`；令 C 为当前点仅含 `at,rules,conflicts,delta` 且按此键序执行 `json.dumps(...,ensure_ascii=False,separators=(',',':'))` 的无换行 UTF-8 字节，`digest` 为 `previous` 的 ASCII 字节紧接 C 的 SHA-256 小写十六进制。`report` 与 `expected` 的 `start`、`end` 或 `root` 不同，或链、任一 `digest`、最终 `root` 不符返回 `False`，否则返回 `True`。
- `POST /explanations`：请求体为恰含 `at,facts,rules` 的 JSON 对象（校验同 `evaluate`）；成功返回顶层键 `at,decision,trace,basis,conflicts`，其中 `basis` 为胜出规则的深副本（无匹配时为 `null`），`conflicts` 仅保留编译结果中涉及该胜出规则的项并保持原顺序。非法请求响应 422 `{"detail":"invalid request"}`，不读写历史。
- `regulation_policy_compiler.policy.decision_attestation(at, facts, rules)`：`at`、`facts`、`rules` 的校验同 `explain`，任一非法时间、事实类型、规则结构、区间或重复规则版本均抛 `ValueError` 且不改输入；只处理传入值，不访问历史或文件。返回深副本，顶层键序 `at,facts,explanation,policy,digest`；`facts` 为输入事实的深副本，键按 Unicode 码点升序（空对象合法）；`explanation` 为 `explain(at,facts,rules)` 的完整深副本并保持各层规范键序；`policy` 为同一时点同一规则的 `compile_rules(at,rules)` 完整深副本（含全部冲突，不省略）。令 C 为仅含前四项且按此键序执行 `json.dumps(...,ensure_ascii=False,separators=(',',':'))` 所得无换行 UTF-8 字节，`digest` 为 C 的 SHA-256 小写十六进制 64 字符；同值输入无论字典原顺序如何均逐字节相同。返回值各分支不共享可变容器，调用方修改结果不影响输入或后续等值调用；空事实、空规则、无匹配决策照常产生凭证，不另设特殊错误。
- `POST /explanations/attest`：请求体为恰含 `at,facts,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}` 且不产生部分凭证，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史，历史未配置也不影响。
- `regulation_policy_compiler.policy.verify_decision_attestation(report, expected)`：纯函数校验单时点决策凭证，不访问历史或文件、不改任何层级的输入。`report` 恰含 `at,facts,explanation,policy,digest` 并逐层符合 `decision_attestation` 返回契约；`at` 为合法 UTC 秒，`facts` 仅允许非空字符串键和布尔值（空事实合法），`digest` 为 64 位小写十六进制字符串。`policy` 恰含 `at,rules,conflicts` 且其 `at` 与凭证 `at` 一致；规则在该时点须落入 `[from,to)`（`to` 为空则不限）、每个 `(source,id)` 唯一，并按 source（law 先于 org）、priority 降序、from 降序、id 的 Unicode 码点升序、ver 降序精确排列；`conflicts` 须等于由该规则序列按下标 i<j（result 不同且 when 可同时成立，前项为 winner）完整重建的冲突序列，缺失、伪造、重复、乱序均非法。`explanation` 恰含 `at,decision,trace,basis,conflicts` 且其 `at` 与凭证 `at` 一致；以凭证 `facts` 对 `policy.rules` 按 `explain` 契约求值并整体比对——无匹配时 `decision`、`basis` 为 `null` 且 `trace`、`conflicts` 为空，有匹配时 `decision` 为排序最高匹配规则的 `result`，`trace` 列出全部匹配规则的 `id@ver`，`basis` 为该规则快照，`conflicts` 按原序保留涉及该 basis 的冲突；决策、轨迹、胜出依据与相关冲突彼此不吻合均为非法。`expected` 恰含 `at,digest`，时间与摘要格式分别沿用上述约束，不接受其他字段。任一层级的键集、类型、时间、事实、规则、冲突或解释语义非法均抛 `ValueError`；两份输入先完整通过结构与语义校验，再做任何比较，避免短路掩盖坏报告。随后按凭证契约重建规范键序（`facts` 及规则 `when` 键按 Unicode 码点升序），以仅含 `at,facts,explanation,policy`（按此键序）的紧凑 UTF-8 JSON 字节（非 ASCII 不转义、无末尾换行）重算 SHA-256 小写十六进制摘要。报告声明摘要与重算值不同，或报告的 `at`、`digest` 与 `expected` 不符返回 `False`，全部一致才返回 `True`。
- `POST /explanations/attest/verify`：请求体为恰含 `report,expected` 的 JSON 对象；解析失败、非对象、键集错误或函数抛 `ValueError` 均响应 422 `{"detail":"invalid request"}`，成功仅返回 `{"valid":bool}` 的 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史、不访问文件，历史未配置也照常完成验证。
- `regulation_policy_compiler.policy.decision_timeline(start, end, facts, rules)`：`start`、`end` 须为合法 UTC 秒且 `start<=end`，`facts`、`rules` 校验同 `explain`，任一非法抛 `ValueError` 且不改输入。候选时点为 `start` 及规则中落在 `(start,end]` 的 `from` 与非空 `to`，去重升序后逐点调用 `explain`；首点保留，后续仅保留相对上一保留点有变化的点。返回深副本，顶层键序 `start,end,points`；点键序 `at,decision,trace,basis,conflicts,changes`，前五项取对应 `explain` 值，首点 `changes=[]`，后续按 `decision,trace,basis,conflicts` 顺序列出变化字段。
- `POST /decision-timeline`：请求体为恰含 `start,end,facts,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史。
- `regulation_policy_compiler.policy.decision_timeline_attestation(start, end, facts, rules)`：`start`、`end`、`facts`、`rules` 的校验同 `decision_timeline`，任一非法时间、事实或规则均抛 `ValueError` 且不改输入；只处理传入值，不访问历史或文件，空事实与空规则仍合法。返回深副本，顶层键序 `start,end,facts,timeline,policy,digest`；`facts` 为输入事实的深副本且键按 Unicode 码点升序；`timeline` 为同区间 `decision_timeline` 的完整深副本并保持其各层规范键序；`policy` 为同区间同规则 `policy_schedule_attestation` 的完整深副本（含 root、快照、差量与哈希链）。令 C 为仅含 `start,end,facts,timeline,policy` 且按此键序执行 `json.dumps(...,ensure_ascii=False,separators=(',',':'))` 所得无换行 UTF-8 字节，`digest` 为 C 的 SHA-256 小写十六进制 64 字符；等值输入无论字典原顺序如何均逐字节相同，各层键序稳定。
- `POST /decision-timeline/attest`：请求体为恰含 `start,end,facts,rules` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史。
- `regulation_policy_compiler.policy.verify_decision_timeline_attestation(report, expected)`：纯函数校验时间线凭证，不访问历史或文件、不改任何层级的输入。`report` 恰含 `start,end,facts,timeline,policy,digest` 并逐层符合 `decision_timeline_attestation` 返回契约；`start`/`end` 为合法 UTC 秒且 `start<=end`，`facts` 仅允许非空字符串键和布尔值（空事实合法），`digest` 为 64 位小写十六进制字符串。`policy` 恰含 `start,end,root,points` 且其时间窗等于凭证时间窗，须完整通过既有 `verify_policy_schedule_attestation` 的结构与语义校验（快照生效区间、唯一 `(source,id)` 与排序、重建冲突、后续点 `policy_delta` 的 added/removed/updated 与冲突差集），再重算其逐点哈希链与 `root`。`timeline` 恰含 `start,end,points`，时间窗须等于凭证时间窗，`points` 为非空数组且点 `at` 严格递增、落在闭区间 `[start,end]`、首点 `at=start`；点恰含 `at,decision,trace,basis,conflicts,changes`，其解释五项符合 `explain` 契约，`changes` 为 `decision,trace,basis,conflicts` 中互不重复的字段名（首点另行与重建结果比对）。所有层级先完成键集、类型、值域与时间校验，再做语义与摘要比较：用凭证 `facts` 对 `policy` 各快照中的全部规则，按 `decision_timeline` 的候选时点（`start` 及落在 `(start,end]` 的 `from` 与非空 `to`）与既有筛选规则重新求值并重建完整 timeline，报告各点的时点顺序、解释内容和 `changes` 须与重建结果逐项一致。`expected` 恰含 `start,end,digest`，时间与摘要格式分别沿用上述约束，不接受其他字段。任一层级结构或语义非法均抛 `ValueError`；两份输入先完整通过结构与语义校验，再做任何比较。随后按凭证契约重建规范键序（`facts` 及规则 `when` 键按 Unicode 码点升序），以仅含 `start,end,facts,timeline,policy`（按此键序）的紧凑 UTF-8 JSON 字节（非 ASCII 不转义、无末尾换行）重算 SHA-256 小写十六进制摘要。嵌入 `policy` 的链或 `root`、报告声明摘要与重算值不符，或报告的 `start`、`end`、`digest` 与 `expected` 不符返回 `False`，全部一致才返回 `True`。
- `POST /decision-timeline/attest/verify`：请求体为恰含 `report,expected` 的 JSON 对象；解析失败、非对象、键集错误或函数抛 `ValueError` 均响应 422 `{"detail":"invalid request"}`，成功仅返回 `{"valid":bool}` 的 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史、不访问文件，历史未配置也照常完成验证。

- `regulation_policy_compiler.history.verify_audit(report, expected)`：纯函数校验审计报告，不访问历史或文件、不改输入。`report` 恰含 `id,start,end,root,entries`，`id` 为非空字符串，`start`/`end` 为合法 UTC 秒且 `start<=end`，`entries` 为非空数组且项 `at` 严格递增并落在闭区间内；项恰含 `at,decision,trace,basis,previous,digest`，前四项沿用 audit 契约，`root`/`previous`/`digest` 为 64 位小写十六进制字符串。`expected` 恰含 `id,start,end,root` 并同法校验；上述非法均抛 `ValueError`，对应字段不同返回 `False`。规范化 `basis` 及 `when` 键序后按 `audit` 定义的 `C`、UTF-8、SHA-256 逐项重算：首项 `previous` 为 64 个 `0`，后项等于前项 `digest`；链、`digest` 或 `root` 校验失败返回 `False`，否则返回 `True`。
- `POST /audits/verify`：请求体为恰含 `report,expected` 的 JSON 对象；解析失败、非对象、键集错误或 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功返回 `{"valid":bool}` 的 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行）。
- `POST /audits/bundle`：请求体为恰含 `record_ids,start,end` 的 JSON 对象；`record_ids` 为非空数组，元素为非空且互不重复的字符串，`start`、`end` 为合法 UTC 秒且 `start<=end`。解析失败、非对象、键集错误、类型或时间校验失败均响应 422 `{"detail":"invalid request"}`，先校验再检查历史；历史未配置或 `audit_bundle` 抛 `OSError` 响应 503 `{"detail":"history unavailable"}`；任一记录在闭区间无数据响应 404 `{"detail":"record not found"}`。成功按 `audit_bundle` 方法契约返回 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），只读历史，不重算规则、不写盘、不改状态。
- `regulation_policy_compiler.history.verify_audit_bundle(report, expected)`：纯函数校验批量审计整包，不访问历史或文件、不改输入。`report` 恰含 `start,end,root,reports`；`start`/`end` 为合法 UTC 秒且 `start<=end`，`root` 为 64 位小写十六进制字符串，`reports` 为非空数组。各子报告须恰含 `id,start,end,root,entries` 并精确符合既有 `verify_audit` 的单份审计报告契约（项恰含 `at,decision,trace,basis,previous,digest`，前四项沿用 audit 契约，`root`/`previous`/`digest` 为 64 位小写十六进制字符串，项 `at` 严格递增且落在闭区间内）；`id` 为非空字符串且在整包内唯一，子报告须按 `id` 的 Unicode 码点严格升序排列，标识重复或报告乱序均为非法结构；各子报告的时间窗须分别等于整包的 `start`/`end`。`expected` 恰含 `start,end,root,record_ids`，不接受其他字段；`start`/`end` 同法校验，`root` 为 64 位小写十六进制字符串，`record_ids` 为非空字符串数组且元素唯一（调用方顺序任意）。任一层级的键集、类型、时间、标识或摘要格式非法均抛 `ValueError`。所有输入先完成结构校验，再做任何比较：随后规范化各 `basis` 及 `when` 键序，按 `verify_audit` 既有语义从每条记录链重算（首项 `previous` 为 64 个 `0`，后项等于前项 `digest`，`digest` 为 `previous` 的 ASCII 字节紧接该条仅含 `at,decision,trace,basis` 的紧凑 JSON 字节的 SHA-256 小写十六进制），不只信任声明摘要；任一子链的 `previous`、`digest` 或该报告 `root` 不符返回 `False`。再按 `audit_bundle` 公开的批量链算法，从规范顺序的子报告重算整包 `root`（h0 为 64 个 `0`，hi 为 h{i-1} 的 ASCII 字节紧接该子报告仅含 `id,root` 的紧凑 JSON 字节的 SHA-256 小写十六进制，root=hn）。`report` 与 `expected` 的时间窗、`root` 或记录标识集合（按码点排序比较）不同，或整包 `root` 不符，返回 `False`，否则返回 `True`。
- `POST /audits/bundle/verify`：请求体为恰含 `report,expected` 的 JSON 对象；解析失败、非对象、键集错误或函数抛 `ValueError` 响应 422 `{"detail":"invalid request"}`，成功仅返回 `{"valid":bool}` 的 UTF-8 紧凑 JSON（非 ASCII 不转义、无末尾换行），不读写历史、不访问文件。
